🎟 Agent Optimization Console

Visibility → recommendations → one-click apply · a teaching surface for the analytics loop
Visibility — what your agents are doing (and what it costs)
Every turn your app runs is captured to Cosmos (OptimizationTurns). These KPIs are the fleet-level view a trace can't give you.
Model usage
Which models actually served your turns. A single model at 100% is the model-selection opportunity: greetings and full itineraries pay the same rate.
Cost by tier
Spend grouped by the tier that served each turn. Before you apply an optimization this is all one tier; after, you can compare — and judge on cost per outcome, not per turn.
Recommendations — detected opportunities
Lower-risk policies (like model selection) can be applied here with one click and reverted just as easily. Higher-risk prompt/code changes are staged for human review instead.
Analytics infrastructure — Fabric capacity
The Fabric capacity that powers these analytics bills while it is running, idle or not. Resume it to refresh the mirror & reverse-ETL, then Pause it when you are done to stop the meter — a cost optimization applied to the very infrastructure doing the optimizing.
The loop
instrument → detect → recommend → apply → verify  ·  policies reach autonomous (L4/L5) behind a quality gate; prompts/code stay human-governed (L3).
This console reads the same Cosmos data the app writes, and applies optimizations through the /optimizations REST API — the same surface an automated (L4/L5) controller would use. It is a provided teaching artifact; in the workshop you write the loop logic, not this UI.
